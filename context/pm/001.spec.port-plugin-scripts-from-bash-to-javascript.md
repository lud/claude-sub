## Goal

Rewrite `plugins/sub/scripts/*.sh` (about 900 lines, plus a 345-line test suite)
in JavaScript the maintainer can read and review. Behavior stays identical: same
hooks, same commands, same state files, same briefing format.

## Context

The scripts are hard to read for anyone but their author. Most of the difficulty
comes from shell quoting rather than from the logic itself:

- the custom `awk` substitution that renders `templates/briefing.md` safely,
- quoted heredocs with placeholder replacement, so backticks and `$(...)` in
  prose are printed instead of run,
- `jq --arg` plumbing for every JSON record and hook output,
- `setsid … >/dev/null 2>&1 </dev/null &` to detach the finisher.

In JavaScript each of these is a direct operation: string replacement, JSON
built-ins, `execFileSync("herdr", [...args])` with no shell in between, and
`spawn(..., { detached: true, stdio: "ignore" }).unref()`.

## Constraints

- **Reviewable source only.** Compiled binaries (Rust, Go) are ruled out: a
  plugin must not ship artifacts nobody can read. Whatever runs is the code a
  reviewer reads, with its real variable names and no minification.
- **No runtime npm dependencies.** Node standard library only, so installing the
  plugin pulls nothing from a registry.
- **`jq` may remain a requirement** if it helps, but it should become unnecessary.

## Design direction

Plain JavaScript ES modules with JSDoc types and `// @ts-check`, run directly by
`node`. `tsc --noEmit` type-checks it in development only (a dev dependency,
never needed at runtime). This avoids a build step and avoids the artifacts of
TS-to-JS output; what is reviewed is what runs.

The fallback, if JSDoc proves too clumsy, is TypeScript built to unminified JS
that is committed alongside the source.

Layout: one entry point (`scripts/sub.js`) with subcommands — `relay`,
`spawn-hook`, `spawn`, `finish`, `last-spawn`, `parent`, `subs`, `prune` — and a
small `lib/` of modules. `hooks.json` and command pre-runs call
`node "${CLAUDE_PLUGIN_ROOT}/scripts/sub.js" <subcommand>`.

## Open questions

- **Is `node` available where the plugin is used?** This is the deciding
  question, and building to JS does not settle it: plain `.js` still needs a
  `node` on `PATH`, it only lowers the minimum version (type stripping for `.ts`
  needs Node ≥ 22.18). Claude Code's native installer does not bring Node with it,
  while bash is everywhere. The plugin already requires herdr and jq, so one more
  requirement may be acceptable, but that is a choice to make explicitly.
- **Relay cost on every prompt.** The `UserPromptSubmit` relay has no matcher:
  it runs on every prompt of every session where the plugin is enabled, and
  almost always finds no state file and exits. That fast path costs about 10 ms
  in bash and about 55 ms in Node (measured on Node 25.4). Either accept the
  difference, or keep a few lines of bash in front that exit when no state file
  exists and only then start Node.

## Migration

One piece at a time, with the existing `test/run.sh` kept as a black-box check
while scripts move over:

1. `lib.sh` and `relay.sh` first — the simplest script and the one that runs
   most often. This step shows whether the result is actually readable before
   the rest is committed to.
2. The spawn path: `spawn-hook.sh`, `spawn.sh`, `finish-spawn.sh`,
   `last-spawn.sh`.
3. `parent.sh`, `subs.sh`, `prune.sh`.
4. Replace `test/run.sh` with `node:test`.

## Out of scope

Behavior changes of any kind. Anything found along the way goes in its own
document.
