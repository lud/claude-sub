## Goal

Rewrite `plugins/sub/scripts/*.sh` (about 900 lines, plus a 345-line test suite)
in a language the maintainer can read and review. What the user and the models
see stays identical: same commands, same briefing format, same reports, same
prune rules. The internals may change where the new runtime makes a mechanism
unnecessary (the relay state file, the detached finisher).

## Context

The scripts are hard to read for anyone but their author. Most of the difficulty
comes from shell quoting rather than from the logic itself:

- the custom `awk` substitution that renders `templates/briefing.md` safely,
- quoted heredocs with placeholder replacement, so backticks and `$(...)` in
  prose are printed instead of run,
- `jq --arg` plumbing for every JSON record and hook output,
- `setsid … >/dev/null 2>&1 </dev/null &` to detach the finisher.

Claude Code now supports **mods** (plugins of function hooks): a plugin's
`hooks/hooks.json` names a TypeScript or JavaScript module under `modules`, and
Claude Code runs that module itself, in-process, in an environment with no Node
and no DOM. Everything outside it goes through the engine object `$`. A plugin
installed from a marketplace loads its module at the `user` tier, like any
installed plugin. The API is declared in a `.d.ts` file that the engine writes
for the running build; the facts below were read from Claude Code 2.1.288's.

## Constraints

- **Reviewable source only.** Compiled binaries (Rust, Go) are ruled out: a
  plugin must not ship artifacts nobody can read. Whatever runs is the code a
  reviewer reads, with its real variable names and no minification.
- **No runtime npm dependencies.** Installing the plugin pulls nothing from a
  registry.
- **`jq` may remain a requirement** if it helps, but it should become unnecessary.

## Design: a TypeScript mod

The plugin ships one hooks module, `hooks/register.ts`, plus a few modules it
imports, typed against `Register` from `'claude-code'`. Claude Code runs the
`.ts` source as is: no build step, no `node` on `PATH`, and what is reviewed is
what runs. `claude plugin validate` checks the module the way the engine will
load it, and `tsc -p plugins/sub` type-checks it against the declarations the
engine lays in `.claude-plugin/types/`.

This settles both questions the plain-JavaScript direction left open: Claude
Code itself is the runtime, so nothing needs installing; and the relay becomes a
function call inside the session, not a process started on every prompt.

The capabilities the port leans on, all on `$`:

- `$.process.run({ argv })` runs `herdr` by argument vector, with no shell.
- `$.fs` reads and writes the briefings and the registry files.
- `$.env.get` reads `CLAUDE_CONFIG_DIR`, `CLAUDE_PID`, `HERDR_PANE_ID`, and in a
  sub `SUB_PARENT`, `SUB_NAME`, `SUB_BRIEFING`.
- `$.clock.after` / `$.clock.every` run work that outlives a hook's dispatch.
  Each hook has its own time budget, so anything that waits on Claude Code's
  4–12 s boot runs on a timer, never inside the hook that started it.

### Mapping from the scripts

| Today | In the mod |
|---|---|
| `UserPromptExpansion` hook on `sub:spawn` that blocks the expansion (`spawn-hook.sh`) | a `command.run` hook matching `sub:spawn` that answers `{ text, context }` without calling `next`: no model turn, and `context` tells the parent model about the sub in the same step |
| `spawn.sh`: write briefing, split pane, start session | a `spawn()` function: `$.fs` writes the briefing, `$.process.run` splits the pane, the start is handed to a timer |
| `finish-spawn.sh` detached with `setsid` | a `$.clock` timer polling `herdr agent get <pane-id>`; no child process to detach |
| `relay.sh` on `UserPromptSubmit`, draining `.state/<session>.jsonl` | the finisher calls `$.session.append` with a hidden user row the model reads on its next turn, and `$.ui.toast` when a sub is `blocked` at a dialog; no state file, no rename claim |
| `/sub:delegate` skill, briefing as a Bash heredoc to `spawn.sh` | a tool, `$.tool.register` → `mcp__sub__spawn({ task, briefing, model?, name? })`; the briefing is a JSON parameter, so it never crosses a shell and needs no Bash permission |
| `subs.sh` reading this session's transcript for reports | a `session.receive` hook on peer messages records which sub reported, as it arrives, in `$.state` and `$.store` (so prune survives a compaction and a resume) |
| `parent.sh` reading `SUB_PARENT` | `$.env.get('SUB_PARENT')`; in a sub, a `prompt.compose` hook adds the sub protocol (parent address, task, duty to report) as a system prompt section, so it survives compaction without re-reading the briefing |
| `prune.sh` | the same rules, with `herdr agent prompt … /exit` and `herdr pane close` through `$.process.run` |
| `lib.sh` | plain modules: nickname, model, geometry, name allocation |

`session.receive` reports a sender's identity only as the sender claims it. It
is good enough to mark a sub as reported, never to gate anything on.

### Keep the markdown commands

`$.command.register` names cannot contain `:`, so a mod-registered command
would be `/spawn`, not `/sub:spawn`. The markdown commands under `commands/`
stay: they keep the namespaced names and remain the fallback path. The mod
answers them through `command.run` hooks matching `sub:spawn`, `sub:report` and
`sub:prune`.

### Layering

The "every automatic path degrades to a manual one" rule from the README stays:
if the module does not load (older CLI, a policy refusing plugin modules), the
markdown command bodies run as they do today.

## Fallback: plain JavaScript on Node

If the mod route fails one of the open questions below, the port falls back to
plain JavaScript ES modules with JSDoc types and `// @ts-check`, run by `node`
with no build step: one entry point, `scripts/sub.js`, with subcommands
(`relay`, `spawn-hook`, `spawn`, `finish`, `last-spawn`, `parent`, `subs`,
`prune`), called from `hooks.json` and the command pre-runs. That route makes
`node` a requirement, which Claude Code's native installer does not bring, and
makes the per-prompt relay cost about 55 ms instead of 10 ms in bash (measured
on Node 25.4).

## Open questions

To answer with a spike in a hot-reloaded mod folder before migrating:

- **Can one `hooks.json` hold both `modules` and classic command hooks?** If
  not, the layering above needs another shape.
- **Does a `command.run` hook fire for a plugin's markdown command**
  (`sub:spawn`), and does answering without `next` skip its `!` pre-run?
- **Does a timer survive long enough for the boot wait?** A module reload drops
  its timers; a spawn in flight during a reload would lose its finisher.
- **Does `CLAUDE_PID` reach the module through `$.env`**, so the parent's own
  nickname is still readable from `<config-dir>/sessions/<pid>.json`? The API
  exposes no session nickname.
- **API stability.** The mod API is marked early access and may change between
  releases without notice, where classic command hooks are stable. The README's
  "Facts this relies on" list is the place to record what the port depends on
  and on which version it was probed.

## Migration

1. Spike: the `sub:spawn` command answer, the timer finisher and the
   `$.session.append` notice, in a mod folder outside the plugin. This answers
   the open questions and shows whether the result is actually readable before
   the rest is committed to.
2. The spawn path: `spawn-hook.sh`, `spawn.sh`, `finish-spawn.sh`,
   `last-spawn.sh`, `relay.sh` and `lib.sh` move into the module; the
   `UserPromptExpansion` and `UserPromptSubmit` entries leave `hooks.json`.
3. `/sub:delegate` becomes the `mcp__sub__spawn` tool, and the skill is
   rewritten to call it.
4. `parent.sh`, `subs.sh`, `prune.sh`.
5. Replace `test/run.sh` with `*.test.ts` under `claude plugin test`. Tests run
   with no file, network or process access and with a mocked clock, store and
   env, so the `herdr` stub on `PATH` becomes hooks answering `$.process.run`
   beneath the plugin.

## Out of scope

New behavior. These belong in their own documents:

- a pane or status line entry listing this session's subs and their state, with
  prune and focus buttons;
- `SendMessage`'s `notify_when_idle`, a one-shot notice when a session on this
  machine goes idle or exits, as a way to learn that a sub stopped without a
  report.
